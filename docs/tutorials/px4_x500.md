# PX4 X500 flight from Robot Lab

Select **px4_x500**, **Gazebo**, a world, and **PX4 Flight** in Robot Lab GUI.
Start with **nav_empty** or **nav_obstacle**, which have measured flight screens.
The command box fills automatically. Start the simulation, wait for PX4 to
initialize, then press **Takeoff** in Drive. The drone remains disarmed when
the simulation or keyboard/joystick control is enabled.

Takeoff climbs 3 m above its initial position. Forward/Reverse, Left/Right,
Strafe and WASD/joystick control body-frame horizontal travel and yaw.
**Altitude Up** and **Altitude Down** climb and descend using the same linear
velocity increment and braking settings as Drive. Click once to latch a
direction, then click it again to slow to a hover; the opposite button changes
direction. Altitude is bounded to 0.5–10 m above the configured ground reference.
Release input to hold position. **Space**, **Stop**, or **Hold** stop manual travel, including altitude changes;
**Land** starts PX4 landing and automatic disarming. Land before ending a
flight; the launch Stop button closes the entire simulation.

This profile uses the real upstream X500 motor/sensor dynamics and PX4
v1.16.2 flight control, in Gazebo Harmonic. The other wheeled profiles continue
to use their existing backends. `quadrotor_sitl` is a legacy display fixture;
its former zero-thrust MAVROS example is retired. Zero thrust cannot hover.

The measured results are in
[October 2 flight evidence](../status/evidence/r54-flight-2026-10-02/README.md)
and [October 5 altitude/additional-world evidence](../status/continuation-2026-10-05.md).
Flight mode supplies Offboard control, FCU estimation and 3D position goals.
It does not supply obstacle avoidance, ground Nav2, LiDAR/RGB-D SLAM, flight
in other backends, or qualification of every map. All installed worlds are
selectable; remaining floor/ceiling/spawn and flight checks are R5.10. Flight
does not automatically avoid walls or furniture.

## Run from a terminal

```bash
cd /workspace/molar/ros_ws/bumperbot_ws
source scripts/ssd_env.sh
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch robot_lab_bringup simulated_robot.launch.py \
  robot_model:=px4_x500 simulator:=gazebo mode:=flight \
  map_name:=nav_empty gui:=true start_rviz:=true
```

Display mode opens the same actual model, with takeoff disabled. RViz uses
the upstream X500 visuals, measured rotor JointState messages, and FCU pose
TF. `/px4/odometry_truth` is separate Gazebo body truth; it is never fed into
the flight controller. FCU and Gazebo data use ROS wall-time stamps in this
adapter. The NED estimator origin is aligned once to the configured spawn;
subsequent motion uses measured FCU state. Normal estimator drift remains.

In another terminal with the same ROS environment/domain:

```bash
ros2 service call /px4/takeoff std_srvs/srv/Trigger '{}'
ros2 topic echo /px4/status
ros2 topic pub --once /px4/goal geometry_msgs/msg/PoseStamped \
  '{header: {frame_id: map}, pose: {position: {x: 1.0, y: 1.0, z: 3.2}, orientation: {w: 1.0}}}'
ros2 service call /px4/hold std_srvs/srv/Trigger '{}'
ros2 service call /px4/land std_srvs/srv/Trigger '{}'
```

Goals use ROS ENU coordinates in `map`; altitude must be 0.5–10 m above the
configured ground reference. The normal RViz 2D Nav Goal belongs to ground
Nav2 robots; publish the 3D PoseStamped above for X500. Manual velocity vectors
are limited to 1 m/s and yaw to 1 rad/s. The adapter sets PX4 horizontal speed
and acceleration limits; it has no collision detector or geofence.

Setpoints stream at 20 Hz while flying. Releasing operator input captures a
position hold; losing the entire adapter invokes the FCU's Land action with
`COM_OF_LOSS_T=0.5` and `COM_OBL_RC_ACT=4`. Normal PX4 GPS/arming checks remain
enabled. This follows the [PX4 v1.16 Offboard contract](https://docs.px4.io/v1.16/en/flight_modes/offboard)
and the [MAVLink position mask](https://mavlink.io/en/messages/common.html#POSITION_TARGET_TYPEMASK).

## Dependencies and reproduction for continuing agents

This host has the pinned checkout/build at
`/workspace/molar/px4/PX4-Autopilot` and the Python environment at
`/workspace/molar/robot_lab_runtime/px4/venv`. PX4 revision is
`54f0455ffcd755534539a7cf33a09a20bf71d29d` (v1.16.2); pymavlink is 2.4.50.
Override `PX4_ROOT` or `PX4_PYTHON` if those paths differ. Do not move the
checkout or build onto Jetson internal storage.

For a new host, use [PX4's pinned Gazebo installation/build instructions](https://docs.px4.io/v1.16/en/sim_gazebo_gz/)
for Harmonic and its build dependencies. Create the checkout and build on the
SSD, pin the revision above, and use a Python environment with system site
packages so sourced ROS Humble modules remain available:

```bash
source scripts/ssd_env.sh
python3 -m venv --system-site-packages "$ROBOT_LAB_RUNTIME_ROOT/px4/venv"
"$ROBOT_LAB_RUNTIME_ROOT/px4/venv/bin/python3" -m pip install pymavlink==2.4.50
colcon build --symlink-install --packages-select \
  robot_lab_registry robot_lab_utils robot_lab_adapter robot_lab_bringup robot_lab_robots robot_lab_gui
```

Rebuild adapter Python files after edits: this host sometimes copies new
modules even with symlink installation. Verify the installed source before
qualifying it. Run one FCU/simulator instance at a time; native PX4 instance 0
uses the fixed local MAVLink port 14580.

For bounded flight evidence, use `scripts/px4_sitl_check.sh` with a new SSD
output directory. For ROS acceptance, launch the GUI-generated Flight command
headless in an isolated ROS domain, then run `scripts/px4_ros_check.py --out
/workspace/path/result.json`. Retain negative trials, source hashes, PX4
revision, pose/rotor results, FCU logs and cleanup. The original `0xFC7`
setpoint mask ignored XYZ; the corrected `0x9F8` requests actual position/yaw.
The script must exit nonzero when acceptance fails, even when PX4 arms.
